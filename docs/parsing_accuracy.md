## 1. 요약

| 검증 | 비교 대상 | 결과 (9건) |
|---|---|---|
| ① 구조 | 표 선 방식(파서) vs 글자 좌표 방식(독립 추출기), 재무제표 3종 모든 숫자 칸 | **2,681 / 2,681 (100%)** |
| ② 의미 | 파서 표준 계정 vs 사람이 페이지 이미지를 읽은 정답표, 14개 핵심 항목 × 당기·전기 | 1차 106/110 → 110/110 · 2차 127/130 → **130/130** |
| ③ 내부 일관성 | 회계 항등식(자산 = 부채 + 자본, 기말현금 BS ↔ CF 등) | **129 / 129** |
| ④ OCR — 숫자 | 같은 2,681칸을 Tesseract 로 읽은 경우 | 개선 전 2,554 (95.3%) → **2,681 (100%)**, 텍스트 레이어 없이 열 배치까지 OCR 로 찾아도 2,681 |
| ④ OCR — 계정명 | 계정명 글자 단위 정확 일치 | 개선 전 127 / 1,372 (9.3%) → **1,164 / 1,372 (84.8%)** |

- **텍스트 레이어에서 숫자를 읽는 단계의 오류는 0건입니다.** DART PDF 는 텍스트 레이어에 원문 숫자가 들어 있어 인식이 아니라 추출입니다.
- **파서 오류는 모두 "어느 숫자가 무슨 계정인가"(의미 매핑)와 메타데이터에서 나왔고 전부 고쳤습니다**(§4). 새 양식이 들어올 때마다 정답표를 늘려야 잡히는 종류입니다.
- OCR 은 개선 전 칸의 4.7% 가 틀렸고 대부분 `1↔7` `3↔8` 같은 **그럴듯한 오답**이었습니다. 원인은 Tesseract 가 아니라 **우리 전처리(표 선 제거)가 숫자 획을 지운 것**이었습니다(§4). 고친 뒤 9건 모든 칸이 일치합니다. 그래도 텍스트 레이어가 있으면 텍스트 레이어가 우선입니다 — OCR 은 스캔 PDF 대비용이고, 이 결과는 깨끗하게 렌더링한 페이지 기준입니다(§6).

## 2. 파싱 방법 (`disclosure_parser.py`)

```
PDF ─▶ ① 텍스트 레이어 확인 ─▶ ② 페이지 분류 ─▶ ③ 표 추출 ─▶ ④ 머리글 해석 ─▶ ⑤ 행 정규화
                                                                                  │
      ⑨ 재무비율 ◀─ ⑧ 회계 항등식 검증 ◀─ ⑦ 메타데이터(감사의견 등) ◀─ ⑥ 표준 계정 매핑 ◀┘
```

| 단계 | 하는 일 | 왜 필요한가 (실제 사례) |
|---|---|---|
| ① 텍스트 레이어 확인 | 페이지에 글자가 있는지, 이미지뿐인지 | 9건 모두 iText 생성 PDF. 이미지 페이지는 운영실태보고서 서명 스캔 1쪽뿐 → 그 쪽만 OCR 대상 |
| ② 페이지 분류 | 페이지 첫 줄(공백 제거)로 `재무상태표`·`손익계산서`·`포괄손익계산서`·`현금흐름표`·`자본변동표`, `주석` 에서 멈춤 | 제목 없는 페이지는 앞 재무제표의 넘김 페이지(백제약품 3종 모두 2쪽) |
| ③ 표 추출 | PyMuPDF `find_tables()` — 셀 테두리 벡터 선으로 행·열 복원 | 일반 텍스트 추출은 셀이 한 줄씩 흩어지고 주석 열이 비면 순서가 밀림 |
| ④ 머리글 해석 | 머리글의 `제 N(당) 기`·`(전)`·`기초` → 기간. 머리글이 빈(None) 열은 앞 기간에 붙임 | 알보젠·아주약품·백제약품은 한 기간이 (세부, 합계) 2열. 같은 표 안에서도 행마다 값이 세부/합계 열을 오감 → 기간별로 값이 있는 열을 채택 |
| ⑤ 행 정규화 | 계정명에서 `Ⅰ.` `I.` `ⅩⅠ.` `(1)` `1.` `가.` `①` 접두어, 주석 참조, 공백·줄바꿈 제거. 금액 `(1,234)` → −1234, `-` → 0 | `자 산 총 계`, `당기손익-공정가치측정금융\n자산`, 주석 참조 표기가 회사마다 다름: `(주석17)` `(주석3과6)` `(주석3,4와6)` `(주7)` |
| ⑥ 표준 계정 매핑 | 동의어 사전(`매출채권` / `매출채권및기타채권`), **`구간:계정`** (유동부채 구간의 `차입부채`), 비용 부호 통일, CAPEX 합산 | 계정명·부호 관례가 회사마다 다름(§4 의 오류 2건이 여기서 났다) |
| ⑦ 메타데이터 | 회사·감사인·기간(당기/전기 일수)·감사의견·회계기준·감사보고서일·감사시간·업종(주석 1 사업 목적) | 판정 문구는 감사보고서 본문 안에서만 찾는다(백제약품 주석의 "한국채택국제회계기준" 문구로 오판한 적 있음). 표지 회사명은 법인격이 붙은 줄 우선(티제이팜은 제목이 먼저 온다) |
| ⑧ 검증 | 회계 항등식 7종 | 추출 오류를 사람 없이 잡는 안전장치. 실패하면 등급을 내지 않는다 |
| ⑨ 재무비율 | 부채비율·유동비율·차입금의존도·이자보상배율·회전일수·FCF 등, 기간 일수 반영 | 아주약품 전기는 28일(물적분할 신설) → 성장률 계산 안 함. 자본잠식(경동사)이면 부채비율 = 무한대(`자본잠식`), ROE 계산 안 함 |

## 3. 정확도 검증 방법

### ① 구조 — 원리가 다른 두 번째 추출기와 대조 (`parsing_accuracy.py`)

파서는 **표 선**으로 칸을 나눈다. 검증기는 선을 전혀 쓰지 않고 **글자 좌표**만으로 표를 다시 만든다.

- 행: y 좌표가 3pt 이내면 같은 줄, 줄 간격이 12pt 미만이면 계정명 줄바꿈으로 보고 한 행으로 합친다(일반 행 간격 14~17pt, 줄바꿈 8pt 실측)
- 열: 금액은 오른쪽 정렬이라 **오른쪽 끝 x 가 모이는 곳**이 열 경계. 열 수 ÷ 기간 수 로 세부/합계 열을 기간에 배정
- 주석 번호(`4,` `5,` `14`)는 기간 머리글보다 왼쪽에 있는 1~2자리 숫자 목록으로 걸러낸다

두 방법이 2,681칸(계정 × 기간) 전부에서 같은 값을 냈다. 1차에서 검증기를 만드는 동안 난 불일치(주석 번호를 금액으로 읽음, 두 줄 머리글, `'　-'` 전각 공백 붙은 대시)는 모두 **검증기 쪽 버그**였다.

### ② 의미 — 사람이 읽은 정답표와 대조 (`tests/fixtures/audit_ground_truth.json`)

재무제표 페이지를 120~130dpi 이미지로 렌더링해 눈으로 읽고 14개 핵심 항목(현금, 자산·부채·자본총계, 단기·유동성장기·장기차입금, 매출액, 매출원가, 영업이익, 당기순이익, 영업활동현금흐름, 기말현금, CAPEX)을 당기·전기로 적었다(재무제표에 없는 계정은 뺀다 — 9건 240값). ①이 "숫자를 제자리에서 꺼냈나"라면 ②는 "그 숫자를 올바른 계정으로 해석했나"를 본다.

### ③ OCR 대조 — 같은 좌표 추출기를 OCR 결과에 적용

같은 페이지를 300dpi 로 렌더링해 Tesseract 5.3(kor+eng)으로 읽고, 텍스트 레이어 결과와 같은 행·같은 기간끼리 비교한다. 세 조건을 잰다.

| 조건 | 하는 일 |
|---|---|
| 1단계 | 표 선 제거 → 페이지 전체 OCR(psm 6) → 숫자 조각 합치기. 열 배치는 텍스트 레이어에서 빌림 (1차 기준선과 같은 조건) |
| 2단계 | 1단계가 찾은 금액 칸만 잘라 **한 줄 모드(psm 7)·숫자 문자(0-9 , ( ) -)만**으로 다시 읽기. 1·2단계가 다르면 400dpi 영문 · 300dpi 한영으로 두 번 더 읽어 다수결 |
| 스캔 조건 | 2단계 + **열 배치·기간 머리글도 OCR 결과에서 찾기** — 텍스트 레이어가 전혀 없는 스캔 PDF 와 같은 조건 |

| 3 | 한 숫자를 겹친 두 조각(`36,930,695,` + `735`)으로 인식, 조각의 y 가 436.8/436.4 로 갈려 다른 줄로 취급 | 끝 조각 `735` 만 금액으로 | 실제 줄(y 중심 연결) 단위로 합치고, 쉼표로 끝난 조각 위에 겹친 조각은 잇기 |
| 4 | 한국어 모델이 `-`(0) 를 `ㆍ` 로 읽음 | 0 → 값 없음 | 대시 모양 글자(`ㆍ` `·` `一` …)를 `-` 로 |
| 5 | 한글을 글자 단위로 내고 글자마다 윗변 높이가 다름 → 윗변 순 정렬이 순서를 섞음 | `기초상품재고액` → `기상재액초품고`, `( 주 석 3)` 이 안 지워짐 | 줄 → x 순서로 조립, 공백 제거 후 주석 참조 제거, OCR 로마숫자 머리표(`|.` `Il.` `Vil,`) 제거 |
| 6 | 스캔 조건에서 머리글 `과 목` 을 `HOS`·`oS` 로, `(당)` 을 `(&)` 로, `제 1(전) 기` 를 `mre)!` 로 읽음 | 열 배치를 못 찾음 (9건 모두 0칸) | 기간 머리글이 둘 이상인 줄을 머리글로, 기수 번호(제40기/제39기)로 당기·전기 판정, 통째로 깨진 머리글은 빠진 기간으로 |

**시험했지만 버린 방법**

| 방법 | 결과 | 버린 이유 |
|---|---|---|
| 숫자 열 전체(세로 띠)를 숫자 전용으로 한 번에 읽기 | 1,568 / 1,750 (기준선보다 나쁨) | `-` 가 사라지고 자릿수가 틀림 — 칸 단위로 잘라야 한다 |
| 해상도·언어 모델 바꾸기(200/400dpi, kor, eng) | 문서마다 오르내림 | 일관된 개선 없음. 원인(#1)을 고치기 전이었다 |
| 계정명 사전 보정(다른 보고서 계정명 중 가장 가까운 이름으로 바꾸기) | 전체 적용 시 1,164 → 1,075~1,142 로 **하락**. 깨진 이름에만 적용해도 바뀐 이름의 26~35% 가 **그럴듯한 다른 계정**(`장기대여금의감소` → `단기대여금의감소`) | 조용한 오답을 만든다 — 깨진 채로 두는 쪽이 안전하다 (자기 문서를 사전에서 빼고 잰 결과) |

- **튜닝에 쓴 문서와 검증 문서를 나눠** 확인했다: 2차 5건을 보며 만든 규칙(#1·#2)을 1차 4건에 그대로 적용해 863 → **925 / 931**(과적합이 아님). 남은 6칸은 1차 문서를 보고 고친 #3·#4 로 931 / 931 이 됐다 — 이 두 규칙은 아직 따로 검증한 문서가 없다.
- 속도: 문서당 약 1분(세 조건 평가 전체, 4코어). Tesseract 의 OpenMP 다중 스레드는 여러 개를 함께 돌리면 서로 기다리며 수십 배 느려져 한 스레드로 고정했다.

```bash
pip install -r requirements.txt            # PyMuPDF

RUN_OCR_TESTS=1 AUDIT_PDF_DIR=/경로/감사보고서 python -m pytest tests/test_ocr_rules.py   # 경동사 1건, 약 1분
```

## 6. 한계

- 표본이 비상장·별도재무제표 감사보고서 9건(의약품 도매·제조, 감사인 6곳)이다. 사업보고서(연결), 반기·분기 검토보고서는 아직 검증하지 않았다.
- OCR 100% 는 DART PDF 를 **깨끗하게 렌더링한 이미지** 기준이다. 종이를 스캔한 PDF(기울기·번짐·잡티·저해상도)는 더 나쁠 것이다 — 실제 스캔본이 생기면 같은 방법(`evaluate(ocr=True)`)으로 재야 한다. OCR 결과는 반드시 회계 항등식 검증을 통과해야 쓰고, 통과 못 하면 등급을 내지 않는다(`score_report`).
- OCR 계정명은 84.8% 로 표준 계정 매핑에 그대로 쓰기엔 부족하다(`매출총이익` → `HSSO]SI`). 스캔 PDF 를 파서에 연결하려면 계정명은 사람 확인이나 위치(행 순서) 기반 매핑이 필요하다.
- 정답표는 14개 핵심 항목이다. 재무제표 전체 칸의 정확도는 ①(두 추출 방법 일치)과 항등식으로 간접 확인했다.
- 주석(차입금 명세, 특수관계자, 우발부채)은 아직 구조화하지 않았다.

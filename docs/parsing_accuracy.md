# 감사보고서 파싱 방법과 정확도

작성: 2026-09-26 · 대상: DART 감사보고서 4건(지오영 · 알보젠코리아 · 아주약품 · 백제약품)
코드: `disclosure_parser.py`(파서) · `parsing_accuracy.py`(검증기) · `tests/test_parsing_accuracy.py`

## 1. 요약

| 검증 | 비교 대상 | 결과 |
|---|---|---|
| ① 구조 | 표 선 방식(파서) vs 글자 좌표 방식(독립 추출기), 재무제표 3종 모든 숫자 칸 | **931 / 931 (100%)** |
| ② 의미 | 파서 표준 계정 vs 사람이 페이지 이미지를 읽은 정답표, 14개 핵심 항목 × 당기·전기 | 수정 전 106 / 110 → **수정 후 110 / 110** |
| ③ 내부 일관성 | 회계 항등식(자산 = 부채 + 자본, 기말현금 BS ↔ CF 등) | **59 / 59** |
| ④ OCR 대조 | 같은 931칸을 Tesseract OCR 로 읽은 경우(선 제거·후처리·열 배치 제공 = OCR 최선의 경우) | 숫자 863 / 931 (**92.7%**) · 계정명 72 / 472 (**15.3%**) |

- **숫자를 읽는 단계의 오류는 0건입니다.** DART PDF 는 텍스트 레이어에 원문 숫자가 들어 있어 인식이 아니라 추출입니다.
- **발견된 오류는 모두 "어느 숫자가 무슨 계정인가"(의미 매핑) 단계에서 나왔고, 2건 모두 고쳤습니다**(§4).
- OCR 로 읽으면 칸의 7.3% 가 틀리고, 그중 72% 는 `3↔8` 같은 **그럴듯한 오답**이라 조용히 잘못된 등급을 만듭니다. 텍스트 레이어가 있는 DART PDF 에 OCR 을 쓸 이유가 없습니다.

## 2. 파싱 방법 (`disclosure_parser.py`)

```
PDF ─▶ ① 텍스트 레이어 확인 ─▶ ② 페이지 분류 ─▶ ③ 표 추출 ─▶ ④ 머리글 해석 ─▶ ⑤ 행 정규화
                                                                                  │
      ⑨ 재무비율 ◀─ ⑧ 회계 항등식 검증 ◀─ ⑦ 메타데이터(감사의견 등) ◀─ ⑥ 표준 계정 매핑 ◀┘
```

| 단계 | 하는 일 | 왜 필요한가 (실제 사례) |
|---|---|---|
| ① 텍스트 레이어 확인 | 페이지에 글자가 있는지, 이미지뿐인지 | 4건 모두 iText 생성 PDF. 이미지 페이지는 운영실태보고서 서명 스캔 1쪽뿐 → 그 쪽만 OCR 대상 |
| ② 페이지 분류 | 페이지 첫 줄(공백 제거)로 `재무상태표`·`손익계산서`·`포괄손익계산서`·`현금흐름표`·`자본변동표`, `주석` 에서 멈춤 | 제목 없는 페이지는 앞 재무제표의 넘김 페이지(백제약품 3종 모두 2쪽) |
| ③ 표 추출 | PyMuPDF `find_tables()` — 셀 테두리 벡터 선으로 행·열 복원 | 일반 텍스트 추출은 셀이 한 줄씩 흩어지고 주석 열이 비면 순서가 밀림 |
| ④ 머리글 해석 | 머리글의 `제 N(당) 기`·`(전)`·`기초` → 기간. 머리글이 빈(None) 열은 앞 기간에 붙임 | 알보젠·아주약품·백제약품은 한 기간이 (세부, 합계) 2열. 같은 표 안에서도 행마다 값이 세부/합계 열을 오감 → 기간별로 값이 있는 열을 채택 |
| ⑤ 행 정규화 | 계정명에서 `Ⅰ.` `I.` `ⅩⅠ.` `(1)` `1.` `가.` `①` 접두어, `(주석17)`, 공백·줄바꿈 제거. 금액 `(1,234)` → −1234, `-` → 0 | `자 산 총 계`, `당기손익-공정가치측정금융\n자산`, `매출채권(주석17)` |
| ⑥ 표준 계정 매핑 | 동의어 사전(`매출채권` / `매출채권및기타채권`), **`구간:계정`** (유동부채 구간의 `차입부채`), 비용 부호 통일, CAPEX 합산 | 계정명·부호 관례가 회사마다 다름(§4 의 오류 2건이 여기서 났다) |
| ⑦ 메타데이터 | 회사·감사인·기간(당기/전기 일수)·감사의견·회계기준·감사보고서일·감사시간 | 판정 문구는 감사보고서 본문 안에서만 찾는다(백제약품 주석의 "한국채택국제회계기준" 문구로 오판한 적 있음) |
| ⑧ 검증 | 회계 항등식 7종 | 추출 오류를 사람 없이 잡는 안전장치. 실패하면 등급을 내지 않는다 |
| ⑨ 재무비율 | 부채비율·유동비율·차입금의존도·이자보상배율·회전일수·FCF 등, 기간 일수 반영 | 아주약품 전기는 28일(물적분할 신설) → 성장률 계산 안 함 |

## 3. 정확도 검증 방법

### ① 구조 — 원리가 다른 두 번째 추출기와 대조 (`parsing_accuracy.py`)

파서는 **표 선**으로 칸을 나눈다. 검증기는 선을 전혀 쓰지 않고 **글자 좌표**만으로 표를 다시 만든다.

- 행: y 좌표가 3pt 이내면 같은 줄, 줄 간격이 12pt 미만이면 계정명 줄바꿈으로 보고 한 행으로 합친다(일반 행 간격 14~17pt, 줄바꿈 8pt 실측)
- 열: 금액은 오른쪽 정렬이라 **오른쪽 끝 x 가 모이는 곳**이 열 경계. 열 수 ÷ 기간 수 로 세부/합계 열을 기간에 배정
- 주석 번호(`4,` `5,` `14`)는 기간 머리글보다 왼쪽에 있는 1~2자리 숫자 목록으로 걸러낸다

두 방법이 931칸(계정 × 기간) 전부에서 같은 값을 냈다. 검증기를 만드는 동안 난 불일치(주석 번호를 금액으로 읽음, 두 줄 머리글, `'　-'` 전각 공백 붙은 대시)는 모두 **검증기 쪽 버그**였고 파서 쪽 오류는 없었다.

| 문서 | 재무상태표 | 손익계산서 | 현금흐름표 | 계 |
|---|---|---|---|---|
| 지오영 (4열) | 80/80 | 32/32 | 72/72 | 184/184 |
| 알보젠코리아 (6열) | 80/80 | 34/34 | 52/52 | 166/166 |
| 아주약품 (8열, 3기간) | 99/99 | 36/36 | 58/58 | 193/193 |
| 백제약품 (5열, 일반기업회계기준) | 146/146 | 98/98 | 144/144 | 388/388 |

### ② 의미 — 사람이 읽은 정답표와 대조 (`tests/fixtures/audit_ground_truth.json`)

재무제표 16쪽을 130dpi 이미지로 렌더링해 눈으로 읽고 14개 핵심 항목(현금, 자산·부채·자본총계, 단기·유동성장기·장기차입금, 매출액, 매출원가, 영업이익, 당기순이익, 영업활동현금흐름, 기말현금, CAPEX)을 당기·전기로 적었다. ①이 "숫자를 제자리에서 꺼냈나"라면 ②는 "그 숫자를 올바른 계정으로 해석했나"를 본다.

### ③ OCR 대조 — 같은 좌표 추출기를 OCR 결과에 적용

같은 페이지를 300dpi 로 렌더링해 Tesseract 5.3(kor+eng)으로 읽었다. 처음엔 표 테두리 때문에 표 영역 전체가 깨진 글자(`'rl'`, `'99999'`, `'season'`)로 나와 0% 였다. 공정하게 비교하려고 OCR 에 유리한 조건을 모두 줬다:
① 표 선 제거 전처리, ② 공백으로 갈라진 숫자 조각 합치기 · 짝 안 맞는 괄호도 음수로 읽기, ③ **열 배치는 텍스트 레이어에서 찾은 것을 그대로 제공**(OCR 이 표 구조를 완벽히 안다고 가정).

## 4. 결과와 발견한 오류

### 파서 오류 2건 (정답표 대조에서 발견 → 수정)

| # | 문서 | 증상 | 원인 | 수정 |
|---|---|---|---|---|
| 1 | 알보젠코리아 | 장기차입금 없음 → 차입금의존도 6.5% (실제 19.4%) | `차입부채` 가 유동부채(200억)·비유동부채(476억)에 같은 이름으로 있는데 첫 번째만 매핑 | 재무상태표 구간을 추적해 `유동부채:차입부채` / `비유동부채:차입부채` 로 구분 |
| 2 | 백제약품 | CAPEX 25.8억 (실제 30.8억), 전기 4.5억 (실제 24.0억) | 현금흐름표가 설비투자를 `건설중인자산의 증가`로 적음. 규칙이 `…의 취득`만 합산 | `…의 취득` 과 `…의 증가`(유형자산 계열만) 모두 합산 |

둘 다 **숫자는 정확히 꺼냈는데 의미를 잘못 붙인** 경우라 ①·③(항등식)으로는 안 잡히고 ②(정답표)로만 잡혔다. 새 양식의 보고서를 넣을 때마다 정답표를 몇 건씩 늘려 가는 것이 가장 효과적인 품질 관리다.

|---|---|---|---|---|

오류 68칸 유형: 숫자 오인식 49 · 부호 오류 5 · 못 읽음 14.

| 원문 | OCR | |
|---|---|---|
| 119,271,73**8**,765 | 119,271,73**5**,765 | 8 → 5 |
| 1,138,**3**13,273,187 | 1,138,**8**13,273,187 | 3 → 8 |

- 숫자 오인식은 겉보기에 정상 금액이라 사람이 표를 봐도 모른다. 항등식 검증이 "틀렸다"는 건 알려 주지만 어디를 어떻게 고칠지는 알려 주지 않는다.
- 계정명은 한글 인식률이 낮아(평균 유사도 0.57) 표준 계정 매핑 자체가 성립하지 않는다(`매출총이익` → `HE SOS`, `기타영업외수익` → `JEP S o| Aol`).
- 속도도 문서당 6~16초(OCR) vs 1초 미만(텍스트 레이어).

## 5. 재현

```bash
pip install -r requirements.txt            # PyMuPDF
# 정답표·구조·항등식 검증 (PDF 4건이 있는 폴더를 지정)
AUDIT_PDF_DIR=/경로/감사보고서 python -m pytest tests/test_parsing_accuracy.py -v
# OCR 대조까지 (Tesseract + 한국어 데이터 필요: apt install tesseract-ocr tesseract-ocr-kor)
python parsing_accuracy.py /경로/감사보고서.pdf --ocr
```

## 6. 한계

- 표본이 감사보고서 4건(비상장·별도재무제표)이다. 사업보고서(연결), 반기·분기 검토보고서, 다른 감사인 양식은 아직 검증하지 않았다.
- 정답표는 14개 핵심 항목이다. 재무제표 전체 칸의 정확도는 ①(두 추출 방법 일치)과 ③(항등식)으로 간접 확인했다.
- 주석(차입금 명세, 특수관계자, 우발부채)은 아직 구조화하지 않았다.
